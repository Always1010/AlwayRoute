# 4A 代理 200 Mbps 可行性、实验撤回与直连测速

> 历史执行快照：日期和结论限于本轮；当前部署见[状态](../status.md)，先后关系见[报告索引](README.md)。私有路径以角色占位，示例命令不是当前操作入口。

2026-10-23，Asia/Shanghai。本记录晚于[完整功能加密优化与刷机记录](2026-10-23-crypto-optimization.md)。本轮最初尝试在保留功能、延迟和稳定性的前提下超过 220 Mbps；用户随后将目标调整为评估能否突破 200 Mbps，若复杂度或投入产出不合适则保持现状，并要求清理实验代码、补测关闭代理的转发能力。

**最终处理：保留当前已安装固件，本轮未打包新镜像、未刷机。未采用的性能实验已从当前源码与构建入口撤回，历史提交及测量证据保留。**

## 结论与适用范围

- 关闭代理后，经过 4A 实际 LAN→WAN 的公网下载最高测得 **185.96 Mbps**；另一个国内源为 **79.48 Mbps**。公网结果受宽带、其他设备共享、上层路由与服务器路径影响，不能当作路由器硬件上限。
- 为排除 200M 宽带限制，额外做了 LAN 侧三层 DNAT/SNAT 回环测试，4 并发、60 秒达到 **638.30 Mbps**。请求与响应均经过 4A，排除了 Rock 本机直接投递。它证明这种受控基础转发路径能明显超过 200 Mbps；**不是 WAN 口极限测试，也不是单连接、无线或所有包长的通用指标**。
- 当前完整代理在同条件 RAM 长测中约 **155–160 Mbps**，CPU 总体接近饱和；此前已安装 Flash 核心的 60 秒结果为 TCP **173.08 Mbps**、WS/TLS **160.88 Mbps**。测试时长、存储条件和附加请求负载不同，不直接用两者计算提升或回退。
- 本轮 VMess 单项读取优化在同条件 180 秒复测中为 **163.44 Mbps**，对照 **160.01 Mbps**，单轮差距约 2.1%，不足以支持稳定突破 200 Mbps。I/O 组合候选又出现核心 panic，未通过稳定性验收。
- 因此，瓶颈主要在 MT7621 上的完整代理处理路径：软件加密、Go 网络 I/O／系统调用与内核网络处理共同耗用 CPU。Flash 容量限制升级余量，但本轮没有证据表明删除界面、规则或协议能解决持续吞吐瓶颈。不能据此断言 200 Mbps 是物理绝对上限；当前证据也不支持继续投入高风险优化来承诺这个目标。

## 四类优化的实施与取舍

| 方向 | 实际试验 | 结果与处理 |
| --- | --- | --- |
| 减少 I/O 小对象分配 | VMess reader 复用 2 字节帧头 scratch、跳过零长度 padding copy；WS reader 复用 12 字节 header scratch | 没有增加预读、等待或改变帧边界。微基准分配下降，完整代理收益较小；组合长测出现 panic，未部署 |
| 精确统计计数器竞争 | MIPS 上用每个计数器独立 mutex 替代共享原子实现带来的竞争；保持立即、完整 64 位统计 | 正确性／并发测试通过，但完整代理收益不稳定；组合 WS/TLS 明显回退，未部署 |
| IRQ、RPS 与线程安排 | 默认 RPS、关闭有线 RPS、扩大 RPS mask、分配物理核/VPE、为 IRQ 留出 CPU 的有限比较 | 关闭 RPS 的短测 TCP 曾约 187.54 Mbps，但延迟增加；其他安排未同时改善 TCP 与 WS/TLS。全部恢复原设置 |
| PGO 与窄内联 | 新采实际透明代理混合 profile；统计锁调用链的窄范围内联；单项及组合构建 | 新 PGO 没有稳定显著收益，统计内联组合存在协议间取舍。未改变当前部署的 PGO、编译设置 |

这些候选此前均通过显式实验参数构建，未成为默认选项。单个候选的 ELF 大小仍为 27,918,491 字节；本轮没有形成经过验收的新固件，也没有取得可以宣称的 Flash 空间节省。

## 代理对照与延迟

受控服务器和源站位于 Rock，批量数据经过 4A 有线 LAN，避免 WAN／公网服务器影响。使用实际配置的脱敏模板，保留完整规则、DNS、sniff、8 个 selector、319 个成员引用及各组当前选择，只替换节点叶子为受控 VMess 服务。实际连接元数据核对 TPROXY、主机名及代理链。

最终长测固定每秒启动一个独立短请求，最多 4 个在途，积压计为失败。4 条下载通过 barrier 起跑，吞吐分母为最早开始到最晚结束的共同墙钟窗口。较早筛选使用“请求完成后再等 0.5 秒”的闭环探针，不能与最终固定频率探针混用延迟结论。

| 同条件 RAM、4 并发、180 秒、固定 1Hz 短请求 | Mbps | CPU 总体 busy | 短请求 p95 | 短请求结果 |
| --- | ---: | ---: | ---: | --- |
| 原版 TCP，首次长测 | 155.34 | 93.26% | 128.40 ms | 179 次，0 错误 |
| 原版 TCP，诊断对照复测 | 160.01 | 92.89% | 131.91 ms | 179 次，0 错误 |
| 仅 VMess framing 候选，TCP | 163.44 | 93.06% | 131.27 ms | 179 次，0 错误 |
| 原版 WS/TLS，长测 | 151.67 | 92.30% | 448.95 ms | 179 次，0 错误 |

CPU 为 `/proc/stat` 差分；MT7621 是 2 个物理核心／4 个 VPE，不应把 4 个逻辑 CPU 当作 4 个独立物理核心。原版 TCP 复测四个逻辑 CPU busy 分别约 91.17%、88.01%、96.94%、95.06%。单项候选并未解除 CPU 饱和状态。

较早 60 秒闭环筛选曾得到原版 TCP/WS-TLS **158.08/150.63 Mbps**、I/O 组合 **174.74/149.66 Mbps**；这支持继续调查 TCP，但不能覆盖后续长测失败，更不能用短测最佳值宣称最终性能。

RAM 测试额外保存约 27 MB 核心文件；长测可用内存最低约 5–9 MiB。上一轮 Flash 测试不需要这份 RAM 副本，也没有本轮固定频率短请求。当前没有刷入候选，所以没有新的“刷后性能”可与上一轮作直接比较。

## 组合候选的稳定性失败

I/O 组合核心 SHA-256：`bbbd1a93ed40c38b2cfe1a2d905264a309636689c40c28f3872e4629790f1fd7`。

第一次 180 秒测试发生 curl 18 提前 EOF；当时异常清理没有保留核心日志，原因无法从该次记录定位。补全失败证据保存后，带 trace 的诊断复测运行到 180 秒，但又观察到一段集中 TCP 重传。该带 trace 结果仅用于诊断，不作为性能验收。

随后关闭 trace 的复测在约 **88.07 秒**，四条下载同时返回 curl 18，保留了明确日志：

```text
panic: inconsistent poll.fdMutex
internal/poll.(*fdMutex).rwunlock
internal/poll.(*FD).Write
net.(*conn).Write
github.com/sagernet/sing/common/bufio.copyExtendedWithPool
```

这是核心进程级失败，不能归因于宽带没跑满。`fdMutex` 是发现不一致的位置，尚未确定最初破坏状态的原因。006 统计锁候选在该核心中没有启用；005/007 与原版使用相同 crypto r2、PGO 和编译 flags。本轮未把未定位的问题草率归为 Go 语言、特定补丁或硬件故障。

新增的持续 65,540 帧差分和 AEAD 计数回绕测试，在 ARM 和 4A MIPSLE 上各 8 个子用例通过；这些测试没有编入实验 r2 汇编，因此只覆盖相应分帧与协议语义，不能代替生产组合的长期稳定性验收。原版又通过一次相同 180 秒对照；单项 framing 的一次通过同样不证明组合故障已修复。

用户随后允许在性价比低时停止。本轮因此停止扩大定位矩阵，没有部署通过牺牲延迟、关闭异步抢占、删除统计或减少协议换取速度的设置。

## 关闭代理后的实测

测试期间正常停止 AlwayRoute，确认 sing-box 进程不存在、TPROXY 规则已撤销，使用基础路由。未改持久配置、RPS 或 offload 设置；完成后恢复原服务和全部策略选择。

| 不开代理，均为 4 并发 | 时长 | 下载吞吐 | CPU 总体 busy | 最忙逻辑 CPU |
| --- | ---: | ---: | ---: | ---: |
| LAN 侧三层 NAT 回环，局域网源站 | 60 秒 | **638.30 Mbps** | 43.70% | CPU2：99.40% |
| 经实际 WAN，清华 TUNA 镜像源 HTTPS | 30 秒 | **185.96 Mbps** | 24.90% | CPU2：73.08% |
| 经实际 WAN，华为云镜像源 HTTPS | 30 秒 | **79.48 Mbps** | 14.22% | CPU2：33.99% |

公网下载使用两个镜像站的 Ubuntu ISO Range 请求，均返回 206；固定 IPv4、源地址及目的地址，不跟随重定向，保留 TLS 证书验证。精确 `/32` 路由将下载从 Rock 有线口送往 4A，逐流核对 local_ip 与 remote_ip。最初 USTC 源返回 403，已作为无效测速记录，**没有把它记为路由器 0 Mbps**。辅助 NAT 规则第一次校验有语法错误，未提交该规则，恢复服务后修正；不属于设备吞吐失败。

LAN 回环路径：Rock 客户端→4A LAN 三层转发→DNAT 到 Rock 源站；通过 SNAT 使源站看到的客户端地址为 4A LAN 地址，确保回程再次经过 4A。源站另外校验该来源地址及临时认证 token。四条源站连接的 peer 均是 4A 地址；转发链记录约 4.826 GB，curl 接收约 4.789 GB，差异包含协议头。测试使用同一有线端口的全双工收发，不能把这个数字改称“WAN 实测 638 Mbps”。

内核 softnet 丢包计数在 LAN 回环／TUNA 测试分别增加 665／616，华为源测试没有增加。它们是整机计数，未逐包归属；单个 CPU 接近饱和及 softnet 丢包提示，更高速转发仍可能受处理能力或接收队列限制，本轮未进一步定位。没有将 638 Mbps 宣称为零丢包、低延迟或长时间稳定的能力。直连流量不终止在路由器 TCP 栈，因此路由器的 `Tcp RetransSegs` 不能用于证明端到端“零重传”。

对家中 200M 宽带，可报告的是此次有效公网下载约 186 Mbps；镜像源变化即可得到 79 Mbps，说明单一公网数值不能定位硬件上限。4A 在受控普通 NAT 路径达到 638 Mbps，而完整代理在约 160 Mbps 已使所有逻辑 CPU 接近饱和，支持将主要优化重点判断为代理处理成本，而非千兆网口不足。
