## 4. 两条路线的后续门槛

1. 原厂路线：固定候选核心，先验证 ELF／内核兼容、显式代理与内存，再测试单台终端透明接管；持久空间、独立启动和完整 Web 管理另行验证。
2. 新固件路线：先获得匹配目标的实际定制核心和完整镜像预算，再准备具体刷机清单。不能把 16 MiB 减下载文件大小视为可写空间。
3. Hysteria2 出站与局域网 UDP 接管分别验证；缺少 TUN／TPROXY 不直接证明 Hysteria2 出站不可用。不存在 `/dev/net/tun` 也不能单独证明内核没有 TUN 能力。
4. Rock 保持辅助角色；正常使用不得依赖 Rock 提供转发、网页或每次启动供给核心。

## 6. 原厂核心兼容与 VMess 实测

### 6.1 候选包检查

OpenWrt `sing-box-tiny 1.13.21-r1` 包从官方 HTTPS 获取，SHA-256 与前次核算记录一致：`75fc4a312136c3e607ee92a1f07dd67949d513c1efa6b85b56f148446a1565ac`。提取 ELF 为 35,384,064 字节，依赖 `/lib/ld-musl-mipsel-sf.so.1`、libc.so 与 libgcc_s.so.1；原厂系统使用 uClibc 且缺少该加载器，因此没有在路由器上执行这个包内二进制。

### 6.2 静态构建

- ELF 无动态解释器，已在 4A 输出版本与上述构建 tag。

### 6.3 启动提交检查

在原厂 `vm.overcommit_memory=0` 下，初次执行被 SIGKILL 终止。最初怀疑 32MiB cgroup 上限，但统计显示 failcnt=0、最高使用仅 384KiB，不支持 cgroup OOM 解释。进一步定位到 Go 加密库的 `crypto/internal/fips140/drbg.memory` 有 32MiB BSS 静态预留区；这不等于实际占用 32MiB 物理内存。

在独立定时恢复保障下，临时将 `vm.overcommit_memory` 设为 1，并保留 32MiB 试验 cgroup 限制后，版本检查和代理启动成功。每次测试均恢复为原值 0，没有写入 sysctl 持久配置。该结果支持启动时内存提交检查是阻碍因素；没有修改加密库或缩减其安全功能。长期方案仍需解决启动条件，不能将临时调参直接视为可交付自启方案。

### 6.4 实际节点测试

只读读取电脑当前 Clash Verge 生成配置，按实际观察到的扁平 VMess 字段解析；选取一条有效格式的 VMess 节点。没有安装 YAML 依赖、修改电脑代理或切换电脑节点。

- 单条节点配置通过 SSH 传到 Rock 受限目录，再传入 4A 的 `/tmp`；未发送到公共转换服务，未写进仓库或聊天。
- 核心在 `192.168.31.1:18080` 临时提供带认证的显式代理，最终出口只有该 VMess 节点，无直连回退。
- Google generate_204：HTTP 204，TLS 校验 0，单次约 0.314 秒。
- 百度：HTTP 200，TLS 校验 0，单次约 0.405 秒。
- 采样 RSS 为 10,740KiB、线程 8；cgroup 匿名内存等计费峰值约 2.84MiB。cgroup 计费不等于完整进程工作集，不能替代 RSS。
- `/tmp` 中另有约 30.1MiB 可执行文件；RSS 与文件映射存在重叠，不能直接相加得到精确总内存。内核未提供该进程的 smaps，未取得 PSS。
- 这是短时、单节点、两次请求，不是吞吐、并发或稳定性验收，也未验证其他协议的真实连接。

测试后已停止核心，删除路由器临时二进制、配置、日志和试验 cgroup，并删除 Rock 单节点配置。18080／1122 已关闭，仅保留 LAN 的 SSH 122；overcommit=0。清理后一次 MemFree 采样为 57,968KiB、Shmem 768KiB。

### 6.5 其他协议的补充检查

使用 Rock 原有 PyYAML 只读解析电脑保存的配置，没有安装解析依赖；取少量样本转换为单出口配置，沿用已有安全参数，不设直连回退。使用同一禁用内联候选、32MiB cgroup 和受保护的短期 overcommit 调整。结果保存在 Rock 私有备份目录的 `mixed-protocol-validation*.json`；原始错误日志仅在 Rock 受限目录。

| 协议 | 配置校验 | 实际连接结果与解释 |
| --- | --- | --- |
| Hysteria2 | 通过 | 两个样本均为 QUIC 会话超时，未证明连接成功；样本原有 `skip-cert-verify` 为真，测试继承该值，不能据此声称上游证书认证有效 |
| VLESS Reality／Vision | 通过 | 首个 IPv6 出站报 `connect: invalid argument`；改取 Rock 可建立 TCP 连接的 IPv4 样本后，TLS 证书名校验失败，没有关闭校验绕过错误 |
| Trojan | 通过 | 样本 TCP 超时，Rock 对该样本端口的连接同样超时，暂不足以归因于 4A 核心 |

4A 本轮只观察到 IPv6 回环与链路本地地址，未发现全局地址或默认 IPv6 路由。以上失败不能直接推广为协议不受支持，也不能把配置通过算作连接可用。进一步使用相同源码、Go 版本与功能 tag 构建 ARM64 参考核心，在 Rock 上复核相同 IPv4 样本：Hysteria2 同样会话超时，VLESS 同样证书名校验失败。因此需要继续排查样本、参数转换或共同上游条件，现有证据不足以认定是 4A 架构／内核导致。没有关闭证书校验绕过错误；参考进程已退出，回环监听和含凭证配置已清理。

4A 短时采样 RSS 约 10.2–11.8MiB，cgroup failcnt 均为 0；这些失败连接的占用不代表成功负载峰值。所有临时核心、配置、认证与 cgroup 均已清理，overcommit 恢复为 0，没有修改路由、DNS 或代理防火墙规则。用户进一步确认“目前只确认 VMess 可用，先继续构建”；本轮以 VMess 作为已知有效样本，其他协议保留为后续验收项，不再追加失效样本试探。

## 7. 新固件的实际文件系统容量实验

从官方获取非 V2 的 OpenWrt 25.12.6 sysupgrade 文件，7,668,302 字节，SHA-256 与官方 profiles.json 一致：`56009dfc5a32fbe9b044d8b5839cccb42ee623361c3852b2e57a75ceaa4c0459`。

提取基础 rootfs，以已有 mksquashfs 做实际 XZ／256KiB 重打包。普通用户无法在宿主创建 `/dev/console`，因此用 mksquashfs 的 pseudo device 定义恢复其元数据，未以 root 解包或创建宿主设备。压缩实验统一使用同一参数；未组装可刷固件，未验证启动。

| 项目 | 常规静态编译 | 禁用编译器内联的体积候选 |
| --- | ---: | ---: |
| ELF 字节数 | 31,588,507 | 27,918,491 |
| 基础 rootfs 重打包 bytes_used | 4,330,106 | 4,330,106 |
| 加核心后的 rootfs bytes_used | 11,841,582 | 10,439,926 |
| 核心的实际 rootfs 增量 | 7,511,476 | 6,109,820 |
| 原 kernel 前缀 + 新 rootfs 文件 | 15,177,544 | 13,772,616 |
| 相对 15,204,352 字节目标上限的算术余量 | 26,808 | 1,431,736 |

第二个候选仅增加 `-gcflags=all=-l`，源码和功能 tag 相同；没有删掉 QUIC、uTLS 或管理 API。其 SHA-256 为 `f2abdeffaaec58568d7471e44e0fe0d9557eee6a3011ffc2c6f36fcaac396d76`。该候选随后也在 4A 验证版本、配置和同一 VMess 节点：Google 204、百度 200、TLS 校验均为 0；RSS 采样 11,416KiB，cgroup 峰值 2,723,840 字节。单次请求耗时约 0.85／4.96 秒，与前次时序不同，不能将差异当作有效性能对比。没有吞吐验收，禁用内联对性能的影响仍待验证。其临时文件、凭证与 cgroup 均已清理，overcommit 恢复 0。

常规静态核心与标准基础系统的组合没有实际部署余量。禁用内联候选剩余约 1.37MiB，尚未扣除最终元数据、对齐、完整管理扩展及配置维护空间，不能宣布达标；值得进入原生定制镜像构建验证。以上均为实际 SquashFS 文件的容量实验，仍不是最终可刷镜像。

进一步对同一基础 rootfs 与禁用内联核心比较 XZ 压缩块：512KiB 时 bytes_used 为 10,161,486，1MiB 时为 9,956,354，分别比 256KiB 的 10,439,926 少 278,440／483,572 字节。对应原内核前缀加 rootfs 文件为 13,494,088／13,289,288 字节，仍未计最终元数据与管理扩展。实验当时尚未修改原生构建配置；后续完整镜像因 256KiB 块超限而改为 512KiB，最终结果见 §8。较大块的解压内存与随机读取性能仍待新系统实机验证。

- 顶层 make 最初使用 `-j4`，随后受控停止并保留成果，以 `-j8 V=s` 增量续编，实测可使用 8 个编译工作进程。该段从 `2026-10-22T15:02:36Z` 开始，监督记录 2,661 秒；此时并非从零构建，不将这段时间当作完整冷编译耗时。工作目录保留 30GiB／单次 2 小时保护，最终约 10.74GB，未触及限额。
- 原监控脚本用 `check_output(du)` 统计工作目录，遇到编译临时文件同时被删除时退出；make 当时继续运行。这次监控缺口已通过受控增量续编与保留退出码的独立监督解决，`du` 返回 1 时须仍有有效总字节才被容忍。仓库版监督脚本另经实际验证：已有同目录 make 活跃时拒绝启动第二个构建。
- 初始清单的 93 份公开源码归档均已校验，但并未覆盖后续发现的 OpenSSL `3.5.9`。该归档在 Rock 下载缓慢，后由电脑沿用现有代理对同一官方 CDN 做 HTTP Range 加速，43.81 秒取全 53,279,637 字节，固定 SHA-256 `603f5602e2eef00d77fbd429d34dcd5822bb301757a1bc9cdb24c670f1eb859a` 一致后 rsync 回填。只结束已被替代的归档 curl，原 make 直接继续，未重启本批构建。更新后的清单在 Rock 重新逐项校验为 94／94 一致，无缺失；没有调整 Rock 路由或新建代理服务。
- OpenWrt 默认 `sstrip -z` 会把已实测核心从 27,918,491 字节改为 27,914,477 字节，并改变 SHA。自有包因此仅对本包设置 `RSTRIP:=:`，保留 Go 已经 `-s -w` 处理的原 ELF；最终解出文件与原厂实测核心完全相同。`PKG_FILE_DEPENDS` 同时跟踪外部 ELF、构建信息和许可证，避免下次更新核心仍复用旧包。
- 256KiB SquashFS 块的首次完整打包产生 13,697,028 字节的未附最终 metadata 镜像，超过本轮 13,565,952 字节限制及原厂 OS1 边界。OpenWrt 删除了超限 bin，却把目标错误标为 ignored，使顶层 make 仍返回 0；本轮未将该返回码当作交付成功。
- 仅将压缩块改为 512KiB，再增量构建，保留全部既定包、协议、IPv6 和双频驱动。该轮监督记录约 180 秒，复用工具链和内核对象；全局配置时间戳仍触发内核重新链接及部分依赖包重建。较大压缩块的解压内存和随机读取性能尚未在新系统实机验证。
- 随后按用户要求执行唯一一次同配置、无源码改动的增量 `make -j8 V=s`，96.172 秒结束、退出码 0；交叉工具链主体及大多数包复用成果，仍包含内核重新链接、少量包编译与镜像重打包。两轮镜像大小相同，但 SHA 改变，未证明逐字节可复现；以下只以这次增量之后检查、归档的具体产物为准，不再构建改写它。`dl/`、`build_dir/`、`staging_dir/` 和 Go 缓存均保留，当前未启用 `CONFIG_CCACHE`，没有执行 clean／dirclean。

## 9. 构建完成后的审查与设备验证顺序

1. 离线镜像结构、SHA、边界、包清单、原核心一致性与审查输入一致性检查已完成，具体结果见 §8。后续只使用上述归档文件及其 SHA；任何重建或功能变更均须重新检查，不以顶层 make 返回 0 单独判定成功。
2. 本候选首启设计为 LAN `192.168.31.1`、SSH 122 仅公钥且仅 LAN、Web 仅回环、无代理自启；输入没有节点与私钥。实际新系统能否按此启动仍待设备验证。内置 LuCI 是基础网络管理，不能代替需求中的完整代理节点／订阅／规则管理。
3. 下一批审查以具体归档文件、两种空间余量、首访路径和恢复清单为依据。当前批准的是离线构建，本轮没有刷写。物理上须可接触 4A 电源和 Reset，恢复网络／TFTP 如需修改 Rock 地址或启动服务，需说明具体动作并另获相应环境变更授权。
4. 新固件的 `firmware` 从 `0x180000` 延伸至 Flash 末尾，覆盖原厂 OS1 和 disk 的地址范围；不能指望原厂 `/userdisk` 内的 SSH 程序、主机密钥和文件在新系统下保留。初始镜像不迁移原厂 Wi-Fi 和管理配置；必要恢复资料已经外置保存于 Rock。
5. 只有进入经审查的设备验证批次后，才检查新系统 root／SSH、LAN／WAN DHCP、基础 HTTPS、无线、overlay 可写余量及重启；然后使用已知有效 VMess 验证内置核心、单终端透明接管、DNS 与故障撤销。其他协议等待已知有效样本。
6. 后续完整交付仍须补齐网页配置事务、订阅与规则管理，并验证掉电／重启、代理故障、断开 Rock 后的独立管理与转发。现有 100Mb/s 管理线链路需要先处理，才能进行千兆吞吐口径的验收；不据当前短时请求承诺带宽。
