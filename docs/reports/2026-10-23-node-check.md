# 单节点与整订阅检测实施及实机验证（2026-10-23）

已在另一聊天完成性能实验收尾后接续实施，并安装到现有 4A。单节点、整个订阅的连通性／代理请求延迟检测已支持串行队列、进度、取消与部分结果保留，不自动选择节点。实测检测期间透明代理连接持续传输，短请求全部成功；同时观察到 CPU 占用和延迟增加，不能称为零影响。

本报告接续[200M 可行性与清理报告](2026-10-23-200m-feasibility.md)。本轮只升级两个管理包，没有重建或刷写整机镜像，也没有修改代理核心、转发包、网络配置或节点选择。脱敏数字见[验证摘要](evidence/2026-10-23-node-check.json)。

## 实现与使用

- 节点页每行的检测按钮检查该节点；订阅页新增“检测订阅节点”图标按钮，仅检查此订阅中已启用、未排除且已加载的节点。
- 后端复用已有短期 ucode worker，通过运行中核心的单节点 delay API 发出小型 HTTPS HEAD 请求，固定测试地址为 `https://www.gstatic.com/generate_204`。逐个完成后才测试下一个节点，没有额外常驻进程或新依赖。
- 页面显示已完成／总数、通过数、失败数及当前节点，支持刷新后重新接回任务。检测时禁止叠加配置操作，正常代理转发继续运行。
- `cancel_check(jobId)` 使用独立的内存取消标志，可绕过检测持有的配置锁。它不会杀死核心或强杀 worker；当前一次有超时限制的探测结束后停止，保留已完成结果。取消请求被接受仍须等待 `job_status` 的 `cancelled` 终态。
- 结果与进度仅写 `/tmp/alwayroute/`，关联已应用 revision，不写检测历史到闪存。新检测不会抹除本次尚未测到节点的旧结果；旧结果仍带原检测时间。
- 当前配置未应用或服务停止时拒绝检测；检测也不会借恢复未完成配置事务之机重启核心。节点检测通过不把整个系统的 `healthy` 改成通过。
- 兼容原单节点返回字段；新增整订阅计数及结果集，RPC 写权限单独包含取消操作。页面普通请求仍为 15 秒超时，检测任务的观察上限为 600 秒，其他后台任务仍为 120 秒；页面等待超时不等于后台取消。

界面 `ms` 为该测试网址的代理请求耗时，包含连接和握手等开销，不是 ICMP ping 或下载带宽。核心超时为 2 秒，已有外部 watchdog 在 3 秒触发终止，必要时再等待 1 秒升级强制结束；界面和 RPC 观察还有额外时间，因此不承诺点击取消后三秒内界面必定完成。单次探测失败也可能来自测试站或链路波动，不代表该节点对所有目标均不可用。

## 构建与包体积

电脑仓库为源码主本。两次同步均先看 rsync dry-run，再同步到 Rock 独立工作副本；仅将两个包分别同步到原 OpenWrt 构建树对应目录。复用已有工具链和缓存，未安装本机依赖、未执行全树清理、未切换核心版本或缓存设置。

定向增量构建 `alwayroute-manager` 和 `luci-app-alwayroute` 成功，约 74.0 秒。管理后端升级为 `1.0.0-r2`，LuCI 包也显式设置 `1.0.0-r2`，便于包管理器识别升级。17 个自有载荷逐文件核对，其中 JS 重放现有 minifier 后比对；可执行入口没有 CRLF。

使用已有构建密钥给归档副本签名，再使用原有公钥严格 `apk verify`、解包与目标机安装。首次给未签名输入补签时的工具调用未产出可用签名，校验拒绝后从原始构建包重新补签并核验；没有将被拒绝的包安装到设备。读取未签名输入的宽松选项仅用于补签步骤，安装和最终验证保持签名校验。

为保持比较条件一致，旧、新管理包均以同一密钥签名后比较；签名编码及压缩会带来几字节差异。

| 软件包 | 原包字节 | 新包字节 | 增量 |
| --- | ---: | ---: | ---: |
| alwayroute-manager | 18,214 | 18,964 | +750 |
| luci-app-alwayroute | 17,307 | 17,947 | +640 |
| 两包合计 | 35,521 | 36,911 | **+1,390，约 1.36 KiB** |

未签名构建产物对应增量为 1,385 字节。其余两个自有包 core、forwarding 保持原样，四个自有包合计约从 8,090,475 增至 8,091,865 字节，增幅约 **0.017%**。这不是新 sysupgrade 镜像尺寸，本轮没有重新打包镜像。

目标机使用仅本地文件、跳过安装脚本的 APK 升级，再重载 rpcd；没有触发代理服务重启。升级前 overlay 可用 1492 KiB，升级后为 1324 KiB：额外占用约 168 KiB 主要来自将 ROM 中管理文件的新版本写入可写层及包元数据，不能与压缩 APK 的约 1.36 KiB 功能增量混为一谈。未为回收这部分空间再次刷机。

## 路由器实测

设备仍为小米 4A 千兆版、现有 OpenWrt 25.12.6／sing-box 1.13.21。使用真实订阅的 38 个 VMess 节点，没有把订阅地址、节点参数、凭据或完整配置写入仓库。

单节点实测通过，返回 1109 ms。整订阅检测完成 38/38，26 个通过、12 个失败或超时，整轮约 69.1 秒；这里的“完成”表示每个节点获得检测结果，不等于所有节点可用。

取消分别验证了尚未开始探测时停止，以及通过真实 LuCI 登录会话在检测中途取消：看到完成 2 个后发出取消，正在进行的第 3 个结束后停在 3/38，已有结果与状态接口一致。认证后的新 RPC、进度读取和取消均成功，HTTP 提供的生产 JS 与已安装文件哈希一致。取消终态、结果保留及随后状态查询的整段确认约 6.3 秒，包含额外状态查询耗时，不作为纯 worker 取消延迟。

转发对照采用 Rock 有线口经 4A 的透明代理，而非让测速流量绕过路由器。仅为两个测试目标增加临时主机路由，测试结束删除。下载 `dl.google.com` 的 HTTPS 文件，限速 512 KiB/s；从 Clash 连接接口确认其链路包含当前代理节点。基线与检测阶段使用同一条长连接，另发起 `www.gstatic.com/generate_204` 短请求，HTTPS 证书验证始终开启。

| 指标 | 检测前基线 | 整订阅检测期间 |
| --- | ---: | ---: |
| 短 HTTPS 请求 | 20/20 成功 | 45/45 成功 |
| 请求中位延迟 | 373.1 ms | 426.5 ms |
| 请求 P95 | 1704.3 ms | 2033.3 ms |
| 路由器总体 CPU 占用 | 6.52% | 30.13% |
| 阶段结束 MemAvailable | 25,892 KiB | 22,164 KiB |

检测期间同一条透明代理连接持续收到 37,431,685 字节（约 35.7 MiB），没有观察到连接重建或中断，45 次进度采样单调增加。全部操作结束后，代理核心 PID、boot ID、8 个策略组选择、revision 13，以及核心和 9 个关键配置文件哈希保持一致；代理、透明转发继续运行，后台任务已结束。

结论限定于本次约 4 Mbps 的正常下载负载：可以边检测边正常转发，但检测有资源成本。单轮公网对照、样本数量及采样操作本身无法严格分离线路波动与检测开销，不能据此给出普遍延迟增幅，也未覆盖接近代理吞吐上限或长期耐久场景。
