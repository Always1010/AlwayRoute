## 故障现场与证据边界

设备可连接无线、分配 DHCP 地址并响应 SSH，系统负载很低，可用内存约 22 MiB，没有发现内存耗尽或内核锁死迹象。WAN 能访问上游网关，但 AlwayRoute 转发处于 guard，客户端 DNS 和两个 HTTPS 请求均超时。

旧实现丢弃 HTTP 工具输出及恢复异常，仅留下最初的切换错误，因此无法从已有日志确定历史请求究竟是传输超时、实际拒绝，还是恢复中的其他阶段失败。当前同一目标的幂等 PUT 实测成功。以下确认的是代码中的错误判定与异步恢复缺口，不把它们冒充为已完整重现历史底层错误。

## 修改

1. PUT 返回非零时，短暂有界读回实际目标。只有已验证的 selector 确认目标选择，才接受丢失响应的请求；提交前仍要确认全部组。最终读回也重试，不能因单次 GET 暂时不可用就重启核心。失败保留数字退出状态，不再直接宣称核心拒绝。
2. 完整重启前读取 procd 管理实例的 PID 和 `/proc` 起始时间。服务在运行却无法确认身份时安全失败；重启后等待旧进程退出、新受管实例运行及全部组匹配，避免把旧 API 或首次可用但未就绪的 API 当作新配置。重启最多轮询 10 次，热切换最终确认 3 次，每次 HTTP 读取另有超时，不等同于固定 10 秒／3 秒。
3. 启动确认复用同一就绪判断。等待耗尽或转发激活失败仍保留 guard；不根据“选择相同”无条件晚到解锁。应用状态新增脱敏的原始失败代码和恢复阶段代码，未知异常归为固定内部错误，不公开原始日志或节点凭据。
